# Container Image Security Policy

> **Version:** 1.0  
> **Effective Date:** July 2026  
> **Scope:** All images in the Evergreen Image Registry (EIR)

## CVE Remediation Policy

### Severity Definitions

EIR uses [Trivy](https://trivy.dev/) severity classifications, which map to CVSS v3 scores:

| Severity | CVSS v3 Score | Examples                                     |
| -------- | ------------- | -------------------------------------------- |
| CRITICAL | 9.0 - 10.0    | Remote code execution, authentication bypass |
| HIGH     | 7.0 - 8.9     | Privilege escalation, SQL injection          |
| MEDIUM   | 4.0 - 6.9     | Information disclosure, denial of service    |
| LOW      | 0.1 - 3.9     | Minor information leaks                      |

### Remediation Timeframes

| Tier                      | CRITICAL    | HIGH        | MEDIUM      | LOW         |
| ------------------------- | ----------- | ----------- | ----------- | ----------- |
| **Critical images** (101) | 7 days      | 14 days     | 30 days     | Best effort |
| **Standard images** (623) | 14 days     | 30 days     | Best effort | Best effort |
| **Community images**      | Best effort | Best effort | Best effort | N/A         |

### Remediation Process

1. **Detection:** Daily Trivy + Grype scans (`daily-security-scan.yml`)
2. **Triage:** New CRITICAL/HIGH CVEs create a GitHub Issue automatically
3. **Assessment:** Check if upstream has a fix
4. **Remediation:**
   - If upstream fix exists → bump upstream version → rebuild
   - If no upstream fix → assess workaround/mitigation → document
   - If no fix possible → document risk, add to risk register
5. **Verification:** Rebuild → re-scan → confirm CVE resolved
6. **Closure:** Close GitHub Issue with evidence

### Auto-Rebuild Triggers

The CI pipeline will automatically trigger a rebuild when:

- A CRITICAL CVE is detected on a critical-tier image
- An upstream version bump is available for a critical-tier image
- The daily scan detects a new vulnerability not present in the previous scan

### Exclusions

Vulnerabilities may be excluded from remediation if:

1. The vulnerable component is not present in the final image (build-stage only)
2. The vulnerability requires conditions not met by the deployment (e.g., local access only)
3. The vulnerability is in an optional component that is not enabled

All exclusions must be documented in `compliance/cve-exclusions.md` with:

- CVE ID
- Affected component
- Justification for exclusion
- Reviewer and date

## SBOM Policy

- Every image MUST have an SPDX SBOM (auto-generated by Syft)
- Every image SHOULD have a CycloneDX SBOM (auto-generated by Syft)
- SBOMs are attached as cosign attestations
- SBOMs are regenerated on every build (no stale SBOMs)
- SBOM changes between builds are tracked and alerted

## Signing Policy

- Every image MUST be signed with cosign (keyless via Sigstore OIDC)
- Every image MUST have SLSA provenance attestation
- Unsigned images should NOT be used in production
- Verification instructions: `docs/verifying-images.md`

## Base Image Policy

### Approved Base Images

| Base                            | Use Case                                         | Example Images                   |
| ------------------------------- | ------------------------------------------------ | -------------------------------- |
| `scratch`                       | Static binaries (Go, Rust, C)                    | redis, traefik, prometheus, nats |
| `cgr.dev/chainguard/wolfi-base` | Images needing glibc + apk                       | nginx                            |
| `cgr.dev/chainguard/<app>`      | Complex apps with Chainguard equivalent          | postgresql-16, mariadb           |
| Upstream repack                 | Apps without Chainguard equivalent (last resort) | vaultwarden, freshrss            |

### Banned Base Images

The following are **prohibited** for new images:

| Base                     | Reason                                                         |
| ------------------------ | -------------------------------------------------------------- |
| `debian` / `debian-slim` | Too large, unnecessary packages                                |
| `ubuntu`                 | Too large, unnecessary packages                                |
| `alpine`                 | musl libc incompatibility, smaller packages available in wolfi |
| `centos` / `rockylinux`  | EOL or unnecessary for container images                        |

> Exception: Build stages (`FROM debian AS builder`) may use any base. Only the **final stage** must use approved bases.

## Non-Root Policy

- All hardened images MUST run as non-root (UID 65532 or app-specific)
- Repack images SHOULD enforce non-root where the upstream supports it
- Images requiring root for initialization MUST drop privileges after init
- The `USER` directive in the Dockerfile is the source of truth

## Health Check Policy

- All images MUST include a HEALTHCHECK directive
- The health-shim binary provides `/livez`, `/readyz`, `/startupz` endpoints
- Images without the shim must provide their own HEALTHCHECK mechanism
