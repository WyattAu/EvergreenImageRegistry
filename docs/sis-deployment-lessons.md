# SIS Deployment Lessons Learned

Infrastructure lessons discovered while deploying SIS to TrueNAS. Each lesson includes what happened, why it happened,
and how to prevent it in future deployments.

---

## LESSON-001: Cloudflare DNS proxy mode requires port forwarding or tunnel routing

| Field                 | Value                                                                                                                                                                                                                                                                                                                                                                                        |
| --------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Lesson ID**         | LESSON-001                                                                                                                                                                                                                                                                                                                                                                                   |
| **Category**          | Networking                                                                                                                                                                                                                                                                                                                                                                                   |
| **Severity**          | Critical                                                                                                                                                                                                                                                                                                                                                                                     |
| **What happened**     | All 19 SIS domains returned Cloudflare 521 (web server is down). A records pointed to the TrueNAS public IP, but the router was not forwarding port 443 to the TrueNAS host.                                                                                                                                                                                                                 |
| **Why it happened**   | Cloudflare proxy mode intercepts traffic and connects to the origin server on port 443. Without port forwarding on the router, Cloudflare cannot reach the origin and returns 521. The router firewall blocked all inbound HTTPS traffic.                                                                                                                                                    |
| **How to prevent it** | Route all domains through Cloudflare tunnel instead of relying on port forwarding. Replace A records with CNAMEs pointing to `<tunnel-uuid>.cfargotunnel.com`. Tunnels eliminate the need for port forwarding and add defense-in-depth. Document the DNS setup in the deployment runbook. Verify each domain resolves correctly with `curl -I https://<domain>` after DNS changes propagate. |

## LESSON-002: Evergreen images don't always respect documented env vars

| Field                 | Value                                                                                                                                                                                                                                                                                                                                  |
| --------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Lesson ID**         | LESSON-002                                                                                                                                                                                                                                                                                                                             |
| **Category**          | Configuration                                                                                                                                                                                                                                                                                                                          |
| **Severity**          | High                                                                                                                                                                                                                                                                                                                                   |
| **What happened**     | The oauth2-proxy Evergreen image ignored `SKIP_PROVIDER_DISCOVERY=true`. The container still attempted OIDC discovery against the issuer URL and failed. Only the upstream `quay.io/oauth2-proxy/oauth2-proxy` image honored the env var.                                                                                              |
| **Why it happened**   | Evergreen repackaging may have changed the entrypoint, stripped shell wrappers that process env vars, or used a different build configuration that doesn't pass env vars through to the binary. The Evergreen image is not a byte-for-byte equivalent of the upstream image.                                                           |
| **How to prevent it** | Test env var behavior by running `docker exec <container> env` and verifying the application actually reads the variable. For complex middleware (proxies, auth servers, gateways), prefer upstream images over Evergreen repackaged versions. Maintain a list of images known to have env var incompatibilities in the image catalog. |

## LESSON-003: Version tag prefixes are inconsistent across registries

| Field                 | Value                                                                                                                                                                                                                                                                                                              |
| --------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| **Lesson ID**         | LESSON-003                                                                                                                                                                                                                                                                                                         |
| **Category**          | Version tags                                                                                                                                                                                                                                                                                                       |
| **Severity**          | Medium                                                                                                                                                                                                                                                                                                             |
| **What happened**     | `vmalert` and `postgres-exporter` require a `v` prefix (`v1.143.0`), but the compose file specified bare versions (`1.143.0`). Additionally, `cadvisor v0.57.0` did not exist as a tag — the correct tag was `v0.47.2`. Docker pull failed for all three images.                                                   |
| **Why it happened**   | Different upstream registries and projects follow different tagging conventions. Some use `v` prefix (GitHub releases), some don't (Docker Hub), and some have gaps in their tag history. The compose file assumed a uniform convention.                                                                           |
| **How to prevent it** | Always verify the exact tag format by running `docker pull <image>:<tag>` before committing versions to `versions.env`. Add a CI step that attempts to pull every image:tag combination in versions.env and fails if any pull returns a manifest unknown error. Maintain a tag-format column in the image catalog. |

## LESSON-004: nginx read-only + cap_drop:ALL requires tmpfs + cap_add

| Field                 | Value                                                                                                                                                                                                                                                                                                                                                                                               |
| --------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Lesson ID**         | LESSON-004                                                                                                                                                                                                                                                                                                                                                                                          |
| **Category**          | Permissions                                                                                                                                                                                                                                                                                                                                                                                         |
| **Severity**          | High                                                                                                                                                                                                                                                                                                                                                                                                |
| **What happened**     | The Taiga gateway nginx container crashed with two errors: `chown failed (Operation not permitted)` and `mkdir /var/cache/nginx failed (read-only filesystem)`. The container was running with `read_only: true` and `cap_drop:ALL`.                                                                                                                                                                |
| **Why it happened**   | nginx needs to write to `/var/cache/nginx` and `/var/lib/nginx/tmp` at startup. With `read_only: true`, these directories must be tmpfs mounts. With `cap_drop:ALL`, nginx lacks `CHOWN` and `DAC_OVERRIDE` capabilities needed to change ownership of files on tmpfs.                                                                                                                              |
| **How to prevent it** | When using `read_only: true`, identify all directories the application writes to and mount them as tmpfs. When using `cap_drop:ALL`, identify which capabilities the application needs (check upstream Docker Compose examples and documentation). For nginx specifically, always add tmpfs for `/var/cache/nginx` and `/var/lib/nginx/tmp`, plus `cap_add: [CHOWN, DAC_OVERRIDE, SETGID, SETUID]`. |

## LESSON-005: Cached Evergreen images prevent upstream pulls

| Field                 | Value                                                                                                                                                                                                                                                                                                                                                                                                        |
| --------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| **Lesson ID**         | LESSON-005                                                                                                                                                                                                                                                                                                                                                                                                   |
| **Category**          | CI/CD                                                                                                                                                                                                                                                                                                                                                                                                        |
| **Severity**          | Medium                                                                                                                                                                                                                                                                                                                                                                                                       |
| **What happened**     | After switching SIS compose files from Evergreen images to upstream images, `docker compose up --pull always` still used the cached Evergreen images instead of pulling the upstream versions. The containers ran with old, buggy binaries.                                                                                                                                                                  |
| **Why it happened**   | Docker uses image tags to identify images. When both the Evergreen and upstream images share the same tag (e.g., `grafana:10.2.0`), Docker considers the cached local image a match and skips the pull. `--pull always` only pulls if the remote digest differs, but if the tag resolves to the same local image ID, no pull occurs.                                                                         |
| **How to prevent it** | Always `docker rmi` cached images before redeploying after switching registries. Use `docker compose up --pull always --force-recreate` to force container recreation. Better yet, use unique image references (e.g., `ghcr.io/upstream/grafana:10.2.0`) that don't collide with previously cached Evergreen tags. Add a `docker image prune -f` step to the deployment script when switching image sources. |

## LESSON-006: Git checkout wipes secrets on TrueNAS

| Field                 | Value                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                          |
| --------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| **Lesson ID**         | LESSON-006                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                     |
| **Category**          | CI/CD                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                          |
| **Severity**          | High                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                           |
| **What happened**     | Running `git reset --hard origin/main` on TrueNAS deleted the `.secrets.tmp/` directory containing all environment variable files (`.env`, `auth.env`, etc.). All services lost their secrets and failed to start after the checkout.                                                                                                                                                                                                                                                                                                                                                                                          |
| **Why it happened**   | The `.secrets.tmp/` directory was not tracked by git (correctly — secrets should not be committed). However, `git reset --hard` restores the working tree to match the committed state, which means any untracked files and directories that exist in the working tree but not in the index are left alone by `git reset --hard` itself — but if the directory was previously committed and then removed from tracking, `git clean -fdx` or a manual rm could wipe it. The actual root cause was that the secrets directory was created manually on TrueNAS and not gitignored properly, so certain git operations removed it. |
| **How to prevent it** | Always re-copy secrets after every git checkout. Store backup copies in a persistent location outside the repo (e.g., `/tmp/secrets_env/`). Add `.secrets.tmp/` to `.gitignore`. Create a post-checkout git hook that copies secrets from the backup location. Document the secret restoration step in the deployment runbook.                                                                                                                                                                                                                                                                                                 |

## LESSON-007: cadvisor needs SYS_ADMIN for container metrics

| Field                 | Value                                                                                                                                                                                                                                                                                                                                                                                          |
| --------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Lesson ID**         | LESSON-007                                                                                                                                                                                                                                                                                                                                                                                     |
| **Category**          | Permissions                                                                                                                                                                                                                                                                                                                                                                                    |
| **Severity**          | High                                                                                                                                                                                                                                                                                                                                                                                           |
| **What happened**     | With `cap_drop:ALL`, cadvisor's `/metrics` endpoint timed out and returned zero metrics (0 lines). After adding `SYS_ADMIN` and `SYS_PTRACE` capabilities, the endpoint returned 12,010 metrics.                                                                                                                                                                                               |
| **Why it happened**   | cadvisor requires `SYS_ADMIN` to read cgroup filesystem metrics (`/sys/fs/cgroup/`) and `SYS_PTRACE` to access `/proc/<PID>/smaps` for memory mapping information. Without these capabilities, cadvisor cannot collect any container metrics and the prometheus scrape times out.                                                                                                              |
| **How to prevent it** | Check application documentation for Linux capability requirements before restricting capabilities with `cap_drop:ALL`. For monitoring agents specifically, expect that they need elevated privileges. Maintain a capability matrix in the service catalog. Test with `cap_drop:ALL` first, then incrementally add capabilities until the service works, and document the minimum required set. |

## LESSON-008: Chainguard/nginx base images listen on non-standard ports

| Field                 | Value                                                                                                                                                                                                                                        |
| --------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------ |
| **Lesson ID**         | LESSON-008                                                                                                                                                                                                                                   |
| **Category**          | Configuration                                                                                                                                                                                                                                |
| **Severity**          | Medium                                                                                                                                                                                                                                       |
| **What happened**     | Chainguard's nginx image listens on port 8080 by default, not port 80. Healthchecks and service URLs configured for port 80 failed to connect.                                                                                               |
| **Why it happened**   | Chainguard images follow a non-root user model. Port 80 requires root or `CAP_NET_BIND_SERVICE`, so Chainguard nginx binds to 8080 instead. The compose file assumed the standard nginx port 80 based on upstream Docker Hub nginx behavior. |
| **How to prevent it** | Always verify the default port for each base image before writing compose configuration. Check the image's documentation, Dockerfile, or run `docker run --rm <image> nginx -T 2>/dev/null                                                   | grep listen` to discover the actual listening port. Document port overrides in the service catalog when they differ from the well-known default. |

## LESSON-009: Distroless images cannot have exec healthchecks

| Field                 | Value                                                                                                                                                                                                                                                                                                                                                                                                           |
| --------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --- | ---------------------------------------------------------- |
| **Lesson ID**         | LESSON-009                                                                                                                                                                                                                                                                                                                                                                                                      |
| **Category**          | Configuration                                                                                                                                                                                                                                                                                                                                                                                                   |
| **Severity**          | Medium                                                                                                                                                                                                                                                                                                                                                                                                          |
| **What happened**     | Tempo (Grafana distroless), redis-exporter (distroless), and zfs-exporter (Evergreen scratch) could not execute shell-based healthchecks. Docker reported `OCI runtime exec failed: exec: "sh": executable file not found`.                                                                                                                                                                                     |
| **Why it happened**   | Distroless and scratch images contain no shell (`/bin/sh`, `/bin/bash`) and no common utilities (`curl`, `wget`). When Docker attempts to exec a healthcheck command like `CMD-SHELL curl -f http://localhost:3200/ready                                                                                                                                                                                        |     | exit 1`, the shell is not found and the healthcheck fails. |
| **How to prevent it** | For distroless/scratch images, choose one of these approaches: (1) Skip healthchecks entirely and rely on external monitoring. (2) Use HTTP GET healthchecks if the image includes `curl` or `wget`. (3) Add `curl` or `wget` to the Dockerfile during the build. (4) Switch to a minimal alpine-based image instead of distroless/scratch. Document the healthcheck strategy per image in the service catalog. |

## LESSON-010: DDNS and Cloudflare tunnel conflict

| Field                 | Value                                                                                                                                                                                                                                                                                                                                                                                                         |
| --------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Lesson ID**         | LESSON-010                                                                                                                                                                                                                                                                                                                                                                                                    |
| **Category**          | Networking                                                                                                                                                                                                                                                                                                                                                                                                    |
| **Severity**          | High                                                                                                                                                                                                                                                                                                                                                                                                          |
| **What happened**     | A DDNS service was creating A records pointing to the public IP, while Cloudflare tunnel needed CNAME records pointing to `<tunnel-uuid>.cfargotunnel.com`. The two mechanisms fought each other: DDNS would overwrite the CNAME with an A record, breaking the tunnel.                                                                                                                                       |
| **Why it happened**   | Both DDNS and Cloudflare tunnel try to manage DNS records for the same domains. DDNS periodically updates A records to reflect the current public IP. Cloudflare tunnel requires CNAME records to route traffic through the tunnel. When both are active, the last write wins and the records oscillate between A and CNAME.                                                                                  |
| **How to prevent it** | Stop the DDNS service entirely when using Cloudflare tunnels. Use tunnel CNAME records exclusively for all domains. Do not mix proxy mode (A records) and tunnel mode (CNAME records) for the same domain — choose one routing method per domain. Document the DNS routing strategy in the deployment runbook. If DDNS is needed for non-tunnel services, exclude tunnel domains from the DDNS configuration. |

## LESSON-011: oCIS microservices bind to 127.0.0.1 by default

| Field                 | Value                                                                                                                                                                                                                                                                                                                                                                                   |
| --------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Lesson ID**         | LESSON-011                                                                                                                                                                                                                                                                                                                                                                              |
| **Category**          | Networking                                                                                                                                                                                                                                                                                                                                                                              |
| **Severity**          | Medium                                                                                                                                                                                                                                                                                                                                                                                  |
| **What happened**     | All oCIS microservices listened on `127.0.0.1` by default. External containers (reverse proxy, monitoring) could not reach them directly. Services were only accessible to each other through the NATS message bus and GRPC service registry.                                                                                                                                           |
| **Why it happened**   | oCIS uses a microservice architecture where inter-service communication goes through NATS/GRPC, not direct HTTP. The default bind address is localhost for security. This is by design but was not understood when writing the initial compose configuration, leading to failed healthchecks and unreachable services from the gateway.                                                 |
| **How to prevent it** | Understand the service discovery model before writing compose configs. Read the upstream documentation for the inter-service communication pattern. For oCIS specifically, configure the gateway to proxy external requests to internal services, and bind monitoring endpoints to `0.0.0.0` if external scraping is needed. Document the architecture decision in the service catalog. |

## LESSON-012: oauth2-proxy OIDC discovery fails through Cloudflare proxy

| Field                 | Value                                                                                                                                                                                                                                                                                                                                                                                                          |
| --------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Lesson ID**         | LESSON-012                                                                                                                                                                                                                                                                                                                                                                                                     |
| **Category**          | Security                                                                                                                                                                                                                                                                                                                                                                                                       |
| **Severity**          | High                                                                                                                                                                                                                                                                                                                                                                                                           |
| **What happened**     | oauth2-proxy OIDC discovery failed when the issuer URL went through Cloudflare proxy. The issuer returned 521 (origin down) or 526 (invalid SSL certificate). `SKIP_PROVIDER_DISCOVERY=true` was ignored by some builds.                                                                                                                                                                                       |
| **Why it happened**   | The OIDC issuer URL pointed to a domain routed through Cloudflare proxy. If the origin server (Keycloak/Authentik) was not yet running or not reachable by Cloudflare, discovery failed. Additionally, some Evergreen builds of oauth2-proxy did not respect `SKIP_PROVIDER_DISCOVERY`, making the env var workaround ineffective.                                                                             |
| **How to prevent it** | Use the internal issuer URL (not routed through Cloudflare) for OIDC discovery. Combine `SKIP_PROVIDER_DISCOVERY=true` with `skip-issuer-verification=true` and explicit `login-url`, `redeem-url`, `profile-url`, and `validate-url` settings. Prefer the upstream oauth2-proxy image which reliably respects these env vars. Ensure the OIDC provider is running and reachable before starting oauth2-proxy. |

## LESSON-013: Keycloak Evergreen image missing Java runtime

| Field                 | Value                                                                                                                                                                                                                                                                                                                                                                     |
| --------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Lesson ID**         | LESSON-013                                                                                                                                                                                                                                                                                                                                                                |
| **Category**          | Scratch libs                                                                                                                                                                                                                                                                                                                                                              |
| **Severity**          | Critical                                                                                                                                                                                                                                                                                                                                                                  |
| **What happened**     | The Evergreen Keycloak image was repackaged without the Java runtime. Container startup failed with `java: not found`. Keycloak requires a JRE to run its Quarkus-based application server.                                                                                                                                                                               |
| **Why it happened**   | The Evergreen repackaging process attempted to minimize the image by copying only the Keycloak server binary and configs, but Keycloak is a Java application that requires a full JVM. The repackager did not account for the Java dependency. This is the same class of bug as BUG-005 (missing runtime tools).                                                          |
| **How to prevent it** | Do not repackage complex application servers (Keycloak, Forgejo, Nextcloud, etc.) into minimal images. These applications have deep dependency trees (JVM, node.js, system libraries) that cannot be reliably replicated in a scratch image. Use upstream images directly. Add a catalog policy that prevents repackaging of images in the "application-server" category. |

## LESSON-014: Forgejo runner version tags differ from release tags

| Field                 | Value                                                                                                                                                                                                                                                                                                 |
| --------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Lesson ID**         | LESSON-014                                                                                                                                                                                                                                                                                            |
| **Category**          | Version tags                                                                                                                                                                                                                                                                                          |
| **Severity**          | Medium                                                                                                                                                                                                                                                                                                |
| **What happened**     | `forgejo-runner:v12.10.1` was specified in the compose file, but this tag does not exist on `codeberg.org/forgejo/runner`. Docker pull failed with a manifest unknown error.                                                                                                                          |
| **Why it happened**   | Forgejo runner uses a different versioning scheme than the Forgejo server. The runner tags on Codeberg may not match the latest Forgejo release version. The version was assumed based on the Forgejo server version rather than verified against the runner's actual available tags.                 |
| **How to prevent it** | Always verify exact tag availability with `docker pull <image>:<tag>` or by checking the container registry's tag list API before committing versions to `versions.env`. Do not assume that component versions match across a project's ecosystem. Add a CI step that validates all image tags exist. |

## LESSON-015: Immich v2 changed API healthcheck paths

| Field                 | Value                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                      |
| --------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Lesson ID**         | LESSON-015                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                 |
| **Category**          | Configuration                                                                                                                                                                                                                                                                                                                                                                                                                                                                                              |
| **Severity**          | Medium                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                     |
| **What happened**     | Immich's healthcheck endpoint changed from `/api/server-info/ping` to `/api/server/ping` in Immich v2.7.x. The compose file used the old path, causing healthchecks to fail with 404 responses.                                                                                                                                                                                                                                                                                                            |
| **Why it happened**   | Immich v2 introduced a major API restructuring. The healthcheck path was changed as part of this restructuring. The compose file was not updated to reflect the new path when upgrading.                                                                                                                                                                                                                                                                                                                   |
| **How to prevent it** | Test healthcheck endpoints from inside the container before committing compose files. Use `docker exec <container> wget -qO- http://localhost:<port>/api/server/ping` to verify the endpoint responds. Subscribe to Immich release notes for breaking changes. Add a comment in the compose file noting the expected response for each healthcheck. When upgrading major versions, review the upstream changelog for API changes that affect healthchecks, environment variables, and configuration paths. |
